Making the server the source of truth

The database was a write-behind cache of browser state. Two changes moved authority to the server: the chat turn became one server action, and the model stopped being fed a copy of every diagram it had ever produced.

The shape of the problem

The schema refactor normalized storage — foreign keys, a real messages table, timestamptz, indexes. But it left authority in the browser. The client still assembled the entire conversation in zustand and shipped it back to be written verbatim, and still decided what the model saw.

Everything below follows from that one fact.

One chat turn

Before

Client drives, DB follows

  1. Append user message to zustandstores/chat.ts
  2. Validate intent — if rejected, return early. Nothing is saved.
  3. Build model context from local historynormalizeChat(currentLocalHistory)
  4. Call the model — if it throws, nothing is saved.
  5. Send the whole conversation back to be overwrittensaveThreadForCurrentUser({ conversation })

Persistence was a side effect of the model call succeeding. A rejected or failed turn ate the user's message.

After

Server drives, client renders

  1. Authorize the sessionrequireAllowlistedCurrentUser()
  2. Persist the user message — before the model is ever calledappendUserMessage() · own transaction
  3. Read history + current diagram from the databasenot from the caller
  4. Call the model
  5. Persist the reply and the new diagramappendAssistantMessage()

One action: sendChatMessage(chatId, clientMessageId, message). The client no longer supplies history, a diagram, or timestamps.

The token bomb

Every assistant message stored a full copy of the diagram, and the old normalizeChat replayed message.diagram || message.message — so every past diagram was re-sent to the model on every request. A Notion schema runs 10–50KB. Context grew quadratically with conversation length; you paid to send the model twenty stale copies of a document it only needed the latest version of.

Before — one diagram copy per past turn After — exactly one, every time

Full diagram copies sent to the model, per request, by turn number.

Now buildModelContext replays message text only (capped at 40 turns), and the current diagram is injected exactly once as the model's last output — so it can still amend it directly.

What each turn now costs

N→1
Diagram copies sent to the model per request, where N is the conversation length.
250→2
Rows written per message. Was a full-array upsert of the whole thread; now two single-row inserts.
~900KB→~1KB
Worst-case action payload. The client used to re-upload the entire conversation on every send.

Verified against real Postgres

The DAL was exercised against a scratch database — not Railway, not your local schema_ai (both untouched). 18/18 checks passed, plus 15/15 unit tests, typecheck, lint and a production build.

  • A user's message survives a failed turn The bug that was eating messages. Committed before the model is called.
  • Another user cannot read, write to, or answer a thread Enforced inside the statement: on conflict (chat_id) do update … where user_id = $n
  • A rejected write leaves nothing behind
  • Re-sending the same clientMessageId is a genuine no-op Double-clicks and retries can't duplicate a message.
  • A rejected intent is persisted, but does not clobber the diagram
  • The second turn's history and diagram come from the database, in send order
  • Deleting a thread cascades to its messages

A diagram is still stored once per assistant message rather than once per version. Storage bloat only — it no longer reaches the model.
